# Campus+ profile-photo storage — staging only, not yet verified with Drive

Profile-photo code is implemented behind `CAMPUS_PROFILE_UPLOADS_ENABLED=1` and per-user `upload_enabled`; both default to off. Automated gateway tests simulate Apps Script and Drive. **No actual Google Drive upload, download, replacement, deletion, or production deployment has been tested. Do not enable this in production until the isolated test below and a security/operational review pass.** Feed attachment code is present behind separate flags; marketplace and other campus attachment modules are not implemented.

## What is implemented

Settings → Profile provides a locked picker for ineligible accounts and a JPEG/PNG/WebP picker, preview, progress, retry, replacement and removal for eligible accounts. The upload endpoint checks the authenticated session and database entitlement, reads a bounded body, checks file signatures and decodes the image with a 16-million-pixel cap, reserves quota in PostgreSQL, then uses the server-only Apps Script adapter. The gateway verifies stored bytes and the database atomically changes the ready association before retiring the previous photo. Downloads check the block-aware `public_profiles` projection and active account status before looking up the private ledger. Successful image responses are served only through Campus+ with private browser caching and mandatory revalidation. Authentication, visibility and the current ready association are checked before returning a checksum ETag or 304; error responses remain no-store. Concurrent reads of the same object within one server process share a Drive download. No Drive ID is returned to the browser. Browser caching and cross-process request reduction have not been measured in a real deployment.

The shared identity mark shows the profile image where a username is provided and retains initials on failure. It is wired to identity lines (including feed and comments), own and public profile pages, the account shell, direct conversation header and list when the other username is present, search results, admin user rows, and ordinary notifications whose actor is visible through the block-aware public profile view. Moderation and system notifications never receive an actor avatar. There is no anonymous photo access: public club/event pages show initials to signed-out visitors. Existing GIPHY media and independent database backups are unchanged.

The default limit is 3 MiB per photo and 25 MiB per account; photo upload attempts are also limited to 20 per hour per account, failing closed if the rate limiter is unavailable. The server validates image decoding but does not run malware scanning or strip image metadata; users should remove location or other embedded metadata before uploading. An existing photo plus its replacement both count toward quota until the old one is deleted. The quota figures reflect Campus+ ledger records, not all contents of the Google account.

## Recovery and operational limits

A reservation remains charged when the outcome is uncertain. Retrying the same selected file in the same page keeps the operation ID and the gateway reuses the deterministic Drive file name; successful finalization makes it ready. Replacement moves the old photo to `delete_pending` only in the same database transaction that makes the new one ready. Removal marks ready and pending operations for cleanup. Quota is released only after the signed gateway confirms deletion.

The gateway serializes operations with a script lock and writes a **permanent Script Properties tombstone** before deleting by upload key; this prevents a delayed retry from recreating a deleted photo. A failure leaves the ledger pending for retry. The `/api/storage/reconcile` cron runs daily and processes a bounded batch of stale reservations and pending deletions. A photo abandoned after upload may stay charged until a later run; failed cleanup stays charged. Request failures, cron downtime and backlogs must be monitored. The gateway's finite Script Properties quota makes permanent tombstones a scaling limit. When quota is exhausted, cleanup and uploads fail closed; there is currently no safe tombstone compaction procedure. Review this limitation before any production release. Deleting Script Properties tombstones manually could allow delayed operations to recreate a file.

The Apps Script uses `DriveApp` to find/create a root folder and locate, create, read and trash files. Its write operations require broad `https://www.googleapis.com/auth/drive` access in this implementation. Folder checks in the code do not restrict the OAuth grant. Use a dedicated Campus+ Google account with no unrelated files. A future Drive API implementation with app-created or explicitly selected files might allow narrower scopes, but is not implemented or verified. The system does not discover, delete, migrate or replace unknown existing Supabase buckets or unrelated Drive files. The database backup system has its own Drive connection and is separate.

## Isolated manual setup and real-Drive test

These instructions require a separate **non-production Supabase project, Vercel project, Google account, and test users**. Do not use a real student photo. Do not change the live project until the test and review are complete. You do not need to edit application JavaScript.

1. **Prepare the test database.** In your isolated Supabase project, apply the repository migrations through your normal migration process, in order through `20261110000004_046_profile_photo_lifecycle.sql`. Review migrations 043–046 first. Migration 045 registers late-created tables with the existing backup capture mechanism; it does not connect or modify the backup Drive account. Never paste the complete schema bundle over an existing production database. Do not run `supabase db push` against production.
2. **Create the folder.** Sign in to Google Drive with the dedicated test storage account. Create a private folder named `Campus+ Uploads`. Open the folder and copy the characters after `/folders/` from its browser address; this is the folder ID. Do not share the folder publicly and do not put its ID in application pages.
3. **Create Apps Script.** While signed in as that same account, open script.google.com, create a standalone project, and name it `Campus+ Test Storage`. In the editor replace the default `Code.gs` with the full contents of `integrations/google-apps-script/Code.gs` from this repository. In Project Settings enable “Show appsscript.json manifest file in editor”; replace the manifest with `integrations/google-apps-script/appsscript.json`. Save. This is a copy/paste step, not an instruction to edit application code.
4. **Set Script Properties.** In Project Settings → Script Properties add `CAMPUS_STORAGE_ROOT_FOLDER_ID` with the folder ID from step 2. Create a long random secret (for example, run `openssl rand -hex 32` on a trusted computer); add it as `CAMPUS_STORAGE_SHARED_SECRET`. Keep this secret private, out of URLs, screenshots, chats and Git. Do not reuse the database-backup OAuth secret.
5. **Authorize the account.** In the Apps Script editor select `setupCampusStorage` from the function menu and click Run. Follow Google's authorization screens while signed into the dedicated account, reviewing the full Drive permission. Verify the execution reports the folder is accessible. Stop if the wrong Google account is selected.
6. **Publish a test web app.** In Apps Script choose Deploy → New deployment → Web app. Set “Execute as” to **Me** (the dedicated Drive owner), and set access to **Anyone** so the server can call it; the signed shared secret protects the gateway. Deploy and copy the `https://script.google.com/macros/s/.../exec` web-app URL. Do not use the `/dev` URL. Creating a new code version does not automatically update an existing deployment: deploy a new version after source changes.
7. **Configure the isolated Vercel project.** In Project Settings → Environment Variables add server-only `GOOGLE_APPS_SCRIPT_URL` with that web-app URL, `GOOGLE_APPS_SCRIPT_SHARED_SECRET` with the exact secret from step 4, and `CAMPUS_PROFILE_UPLOADS_ENABLED` with `1` for the test environment only. Set the existing server-only `SUPABASE_SECRET_KEY` to the isolated project's secret key; never use a `NEXT_PUBLIC_` variable for a secret. Ensure a strong, at least 32-character `CRON_SECRET` is configured for this Vercel project. Vercel sends it to its cron jobs automatically. Deploy the test branch to this isolated Vercel project using your usual manual process; environment changes require redeployment.
8. **Grant one test user.** Sign in as an administrator with `manage_users`; in Admin → Users, find a separate student test account and grant upload permission. New accounts remain disabled, and an administrator cannot grant their own account through this control. Confirm the ungranted test student sees the locked control. Do not grant everyone permission.
9. **Upload and inspect.** Sign in as the granted test student. Open Settings → Profile → Choose photo. Select a small JPEG, PNG or WebP and verify the preview, then press Upload photo. Confirm the image appears after success. In the dedicated Drive folder verify one private `campus-upload-v2-...` file was created. The Drive filename is an internal identifier, not a browser URL. Test a file near 3 MiB and each supported format, plus a malformed and oversized file.
10. **Check access.** With another active test user, view the first student's profile and feed. Verify the avatar appears only through Campus+. Block either user and verify the image endpoint returns no image across the block. Sign out and verify the image endpoint is not accessible. Confirm browser network responses and rendered HTML contain no Drive file IDs, secret or public Drive URL.
11. **Replace and remove.** Upload a different photo; confirm the new image appears and the old Drive file is moved to Trash only after the new photo succeeds. Remove the photo and verify initials return, the new Drive file is trashed, and the account usage falls after cleanup. Simulate a gateway outage during replacement and verify the old photo remains. Restore connectivity and retry the same selected file. Simulate a deletion failure and retry removal; check quota is not released until cleanup succeeds.
12. **Check recovery.** Interrupt an upload after the Drive file is created but before its response reaches the browser. Retry the same selected file without reselecting it and verify only one Drive file is created. Leave an interrupted operation for over one hour and verify the scheduled reconciliation later retires it and releases quota after deletion. Inspect Vercel cron logs and the Admin → Upload storage ledger summary; do not log the secret or file contents. The daily schedule means cleanup is not immediate.

Record actual outcomes. A health check alone does not establish a real round trip. Failed tests are blockers; keep `CAMPUS_PROFILE_UPLOADS_ENABLED=0` while investigating.

## Local verification

Run `npm run lint`, `npm test`, `npm run build`, and `npm run verify`. For disposable PostgreSQL quota, authorization, backup and lifecycle checks, run `npm install --no-save embedded-postgres` followed by `node scripts/dev/storage-profile-db-check.mjs`. Never point the disposable tests at production. Gateway tests use an in-memory Apps Script/Drive simulation, not Google services. `npm run verify:security` additionally requires a configured Supabase environment; without it, report that check as not run rather than fabricating a result.

### V3 profile-photo integration (not ready for rollout)

When `CAMPUS_STORAGE_V3_ENABLED=1`, profile-photo uploads reserve an immutable deadline-bearing V3 key in the ledger and use the gateway's separate V3 namespace. Cleanup dispatches by the recorded key, including when the flag is later off. Downloads of existing V2 photos continue to use their recorded Drive ID. V2 cleanup still creates permanent tombstones: this integration does **not** implement a safe V2 cutover or stop older deployments from issuing V2 uploads. Do not delete legacy tombstones. The gateway still holds one global lock and scans Script Properties; no throughput measurements have been made.

For isolated testing only, apply migration 047 after the prior migrations, publish the updated Apps Script to an isolated gateway, deploy this application against the isolated database and gateway, then set `CAMPUS_STORAGE_V3_ENABLED=1` alongside the existing upload gate and a test account's entitlement. Do not use this as a production cutover procedure. Keep the flag off until the V2 retirement protocol, replay-state cleanup, race tests and real Drive verification are completed. Do not roll back the database or gateway while V3 files or pending cleanup exist; old gateway versions cannot read or delete V3 files. The new application queries the added columns even with the flag off, so apply the migration before deploying it.

### Post attachments: partial staging implementation

Migration 048 expands the existing ledger to include post attachments, records post associations in a private table, shares the per-account quota with profile photos, and retires files on post soft deletion. The existing daily reconciliation endpoint retries post cleanup. For isolated tests, migrations 047 through 050 must be applied in order; use an isolated V3 gateway and set both `CAMPUS_STORAGE_V3_ENABLED=1` and `CAMPUS_POST_ATTACHMENTS_ENABLED=1`, while granting upload entitlement only to selected test accounts. No production deployment is authorized or recommended. The feature preserves the 3 MiB limit and permits up to eight files per post. Deleting a post permanently retires its attachments; restoring the post does not restore them.

This is **not** a completed feed phase: the composer uploads to an expiring private draft before atomically publishing the post and associating its ready files. On submission the browser saves the submitted text, original files and retry identifiers in IndexedDB, and offers resume or discard after navigation or reload. The copy remains in the browser until successful publication or explicit discard; users are warned not to use shared devices. Server drafts expire after 24 hours, and abandoned drafts and failed reservations are eventually reconciled. An expired upload reservation requires discarding and restarting the draft. Owners can edit post body and discussion title; polls remain immutable. Replacement uploads the new image before retiring the old one and requires spare quota and a free attachment slot. Thumbnails are generated on demand, not persisted, and gallery metadata is fetched per visible post. Marketplace and other campus attachments are not implemented. No real browser or Google Drive end-to-end validation has been performed; V3 and V2 cutover limitations above still apply. Keep both attachment flags disabled outside an isolated test environment.
