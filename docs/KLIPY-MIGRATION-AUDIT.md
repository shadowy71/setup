# KLIPY migration: audit and production blocker

**Status: KLIPY client and migration drafted and tested locally; not production-verified.** The legacy GIPHY proxy remains as a rollback artifact. Production has database CHECK constraints that reject KLIPY. The user approved preparing a narrowly scoped migration locally, not applying it to production. A client-only replacement would break posting and messaging. No production settings, data, schemas, code paths, keys or deployments were changed in this audit.

## Production blocker

Read-only catalog inspection of the existing Supabase project found provider and URL-host constraints on each of `public.posts`, `public.comments`, `public.messages`, and `public.random_messages`: non-null GIFs must have `provider = 'giphy'` and their `url` must match the GIPHY host expression. The repository additionally contains a GIPHY-only random-message RPC check. The application validator in `lib/validation/schemas.js` likewise accepts only GIPHY. New `{provider:'klipy', ...}` references cannot be saved until compatible database validation exists; rewriting a KLIPY URL to look like GIPHY would violate provider requirements and must not be done.

A safe implementation needs an explicitly approved, additive change to existing constraints that supports only verified KLIPY media hosts and continues to accept historical GIPHY references; preserve RLS, authorization and old rows. This would be drafted/tested locally first, not applied to production without separate approval. Confirm actual KLIPY host patterns, URL lengths, slugs and tracking parameters from official docs and real test responses before designing constraints; do not loosen host checks indiscriminately. Existing GIPHY URLs need to remain renderable even when new search switches to KLIPY.

## Provider requirements and rollout considerations

KLIPY's [integration requirements](https://docs.klipy.com/integration-requirements) require end-user browser API/media requests in standard integrations, unchanged media URLs and tracking data, preserving result order/composition, and no unapproved server proxy or independent media cache/rehosting. Separate provider sources; seek written approval before custom proxy/caching/mixing. The [attribution guidelines](https://docs.klipy.com/attribution) require the `Search KLIPY` placeholder; the requested picker attribution must use provider-approved branding. [GIF API](https://docs.klipy.com/gifs-api) documents trending, search, categories, items and share operations. Verify exact live response/advertisement handling, CORS, media host/network allowlists, rate limit and branding before enabling; do not silently filter or reorder results. No KLIPY key or live provider access was used during this audit.

The old proxy applies authenticated `use_gifs` and account-status checks plus a server-side shared-quota limit. A public browser API key cannot preserve that proxy as an enforcement point: direct provider calls are inherently accessible outside the Campus+ UI. Preserve server-side write authorization and rate limits as applicable, document the provider-key quota/security tradeoff, and verify the required provider/content-filter settings. Avoid collecting extra user identifiers without a privacy review. The public client key must be configured in Vercel Production, Preview and Development **outside Git**, using the Vercel dashboard or existing secret-management workflow; never put key values in chat or source control. Do not remove the existing GIPHY variable until KLIPY has been verified.

## Implementation status

The shared picker now requests trending/search/categories in the browser using `NEXT_PUBLIC_KLIPY_APP_KEY`, locale `in`, page-based pagination, debounce and abort signals. It retains result order and original media URLs, displays thumbnails and attribution, and validates the reference again before saving. Message/post/comment server actions check `use_gifs`. Historical GIPHY rendering remains. `klipyRequest` supports the items endpoint, but the picker does not currently call it: it selects full GIF references already provided by trending/search. The requested items endpoint workflow remains unverified and is not claimed complete.

A page containing an unsupported result (including an ad) fails rather than silently dropping or rearranging it. Disable ads for the partner key until compliant rendering and tracking are implemented and tested. API response shapes and branding have not been checked against a real key, nor has this picker been tested in a browser. The legacy `/api/giphy/search` proxy and its server config remain until a successful KLIPY verification and subsequent cleanup; the old env values must remain untouched. The application-level `use_gifs` check protects server actions but does not add a new RLS policy or prevent a direct database client from using an otherwise permitted write.

Verification in this turn: `npm run lint` passed; `npm test` passed 151 files and 1,416 tests; `npm run build` passed with placeholder Supabase configuration and no KLIPY key. KLIPY tests use mocked API payloads only. Production configuration and deployment have not been changed.
