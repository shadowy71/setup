# Campus+ — repository and experience audit

**Repository:** `shadowy71/setup` · `main` @ `8ab3eb6` ("Merge pull request #54")
**Audited:** 31 October 2026 · branch `arena/9ed7b5dc-setup`
**Method:** the app itself, running against the repository's own fixture backend (embedded
PostgreSQL + all migrations + seeded data + Supabase stub), driven in a real headless Chromium
at 1440×900 and 390×844. Every claim below is either a measurement from that session or a file/
line that was opened. Where something could not be verified, it says so.

---

## 1. Verdict

This is not a prototype. It is a disciplined, unusually well-documented product with a real
design language, 58 routes, layered authorisation, and a test suite that actually runs.

| Check | Result |
|---|---|
| `npm run build` | **passes** — 58 page routes, 3 route handlers, Proxy |
| `npm test` | **78 files / 970 tests pass** |
| `npm run lint` | **clean** |
| Migrations applied from scratch | **37/37**, no errors |
| WCAG 2.2 AA (axe, 12 signed-in surfaces) | **0 violations** except 1 `definition-list` on `/profile` |
| Console errors in the browser | only the fixture's missing Realtime socket (expected) |
| Horizontal overflow at 390 px | none on the 10 surfaces measured |

The gaps are therefore not "is it built" gaps. They are **first-run experience, information
architecture, typography scale, and repository operations**. Ranked by how much a student would
feel them, that is where the work is.

Two bugs were found that are unambiguously wrong, and **one of them is fixed on this branch**
(§7.4).

## 4. First run: the experience is the problem

### 4.1 Three competing onboarding surfaces on load

Measured on a 390×844 phone, first visit, settled:

| Surface | Where | Size |
|---|---|---|
| Galactic splash | full screen | 5,650 ms (`FADE_AT_MS` 5250, `FINISH_AT_MS` 5650) + up to 3,000 ms font wait |
| "New to Campus+?" guide strip | top of Home | 155 px tall |
| "A quick look around?" tour offer | floating above the dock | 141 px tall |
| `/guide` page + "First-visit guide"/"Quick navigation tour" entries in the menu | separate | — |

Each of these is individually well made — the strip even degrades honestly when storage is
unavailable (`components/guide/GuideWelcomeStrip.js`) and the tour offer is properly dismissed
and positioned. Together they are a queue of prompts asking for the same attention. A student's
first screen is: an intro they must skip, a banner, and a popover, above a feed they did not
ask for yet.

**Recommendation**

1. Keep the splash but make it a *landing* event, not a *reload* event. `components/layout/GalacticIntro.js`
   holds `let completed = false` in module memory, so it resets on every document. Move that flag
   to `sessionStorage` (the repo already has a storage-safe helper in `lib/guide/first-visit`), and
   shorten the repeat visit to a ~600 ms fade.
2. Choose **one** contextual prompt: the strip on Home *or* the tour offer, never both. Gate the
   tour offer behind "guide already acknowledged".
3. Put both dismissals in one place (`Settings → Appearance` or the menu) so "I said no" is
   durable and reversible. The menu already lists "First-visit guide" and "Quick navigation tour",
   which is exactly the right home for them.

### 4.2 The Create menu is a wall of thirteen destinations

`app/(app)/layout.js` builds `createItems` with 13 entries (Post or poll, Discussion, Marketplace
listing, Gig, Community, Study group, Club, Lost & found, Team post, Study request, Event
submission, Resource, Opportunity, Project) and renders them as one flat popover. On desktop it
covers the whole navigation rail; in the mobile menu it is a third of the sheet.

**Recommendation:** group into four rows — *Post* (post/discussion/poll), *Sell or hire*
(listing/gig), *Campus* (lost & found, event, team, study), *Build* (project, resource,
opportunity) — with the three most-used as direct buttons. No permission logic changes: the list
is already server-built, so grouping is presentation only.

### 4.3 Home's preamble is long

On a phone the order is: header → guide strip → greeting hero → 2 CTAs → 3-stat row → "Your
campus, at a glance" (4 tiles) → composer → feed. The feed itself starts below the fold, twice.

**Recommendation:** on viewports under 640 px, keep the greeting + composer, collapse the four
"glance" tiles into a single horizontal scroller (or move them behind the Campus tab), and keep
the stat row as one line. The information is good; the serial layout is what costs.

## 5. Navigation and information architecture

### 5.1 Every destination is a tab stop twice

`components/navigation/NavigationHelp.js` renders an "About <label>" button beside each nav row.
Measured tab order on `/home`:

```
a:Home  button:About Home  a:Explore  button:About Explore  a:Market  button:About Market …
```

The rail renders 11 rows (Home, Explore, Market, Gigs, Clubs, Communities, Campus, Timetable,
Profile, Messages, Notifications); 10 of them also carry an `About` button. That is **21 tab stops
to reach the end of the rail** on every page, because the shell is shared.

**Recommendation:** keep the help content, drop the per-row trigger. Add a single "Navigation
help" toggle (the `?` key, or a `?` button in the header) that switches the rail into a mode
where each row reveals its description — one affordance, no permanent tab-tax. Alternatively mark
the triggers `tabindex="-1"` so they stay mouse/touch-only; the text is already in
`aria-describedby` when opened.

### 5.2 The mobile dock reaches five places; the product has eleven

Dock: Home, Explore, Market, Chat, Profile (`MOBILE_NAV`). Notifications, Clubs, Communities,
Campus, Timetable, Gigs are only reachable through the ☰ sheet. That is defensible, but the
notification *badge* lives in the header while Messages lives in the dock — the two "attention"
destinations are split across two chromes.

**Recommendation:** pick one. Either the dock's fifth slot becomes a "More" that opens the sheet
(and messages move to the header bell group), or Notifications moves into the dock with its badge.

### 5.3 Two search boxes on Explore, and the header one is silent

`/explore` renders the header search field ("Search Campus+…") **and** a page field ("Search
people, posts, communities, events, listings…"). Both work, but the header field does nothing
visually until Enter — no suggestion, no spinner, no hint. Typing in the page field updates
results but leaves the page's own `<h1>`/lede reading "Search, trending, and the modules you
might not have opened yet".

**Recommendation:** (a) on `/explore`, hide the header field; (b) make the header field show a
three-result preview after ~250 ms, which the product already has the pieces for
(`/api/search` + `CommandPalette` styling); (c) when `q` is present, swap the lede for
`Results for “…”` — the URL is already the source of truth.

Positive: the search itself is fast and good. `?q=event` returned 18 grouped results across
events and marketplace in one pass, with scopes, and `⌘K`/`Ctrl+K` opens a genuinely nice
command palette with arrows/enter/esc documented in the footer.

## 6. Layout, typography, density

### 6.1 The width inconsistency is the loudest visual issue

Measured at 1440 px:

| Page | Content box |
|---|---|
| `/home` | `main.shell-content` **1168 px**, x = 272 |
| `/explore`, `/market`, `/clubs`, `/campus`, `/notifications`, `/profile` | `main.shell-content` **768 px**, content column 720 px, x = 472 |

So Home is a full three-column stage and every other page is a narrow column with a **224 px
empty gutter on the right**. It reads as unfinished rather than restrained — the screenshots of
Explore and Market have a third of the viewport doing nothing.

**Recommendation:** define one content scale in `app/globals.css` — e.g. `--content-narrow: 720px`
(forms, settings), `--content: 1040px` (lists, directories, feeds), `--content-wide: 1168px`
(Home) — and centre the narrow/standard tiers in the available width. This is a CSS-variable
change plus one wrapper per page group; it will make the product look deliberate instantly.

### 6.2 Text is too small for a text-first product

Share of visible text nodes rendered below 12 px, on a 390 px viewport:

| Page | below 12 px | most common sizes |
|---|---:|---|
| `/home` | 33 % | 10 px ×16, 11 px ×10 |
| `/explore` | **55 %** | 11 px ×44 |
| `/market` | **56 %** | 11 px ×102 |
| `/clubs` | **62 %** | 11 px ×245 |

Body copy is 13–15 px (fine), but metadata, tags, descriptions, card previews and captions are
10–11 px. On a phone at arm's length that is below comfortable reading, and it is where the
product's actual content lives.

**Recommendation:** raise the floor. Set `--text-2xs: 12px`, `--text-xs: 13px`, and change the
`--text-2xs` token itself — there are 282 `text-2xs` occurrences across `app/` and `components/`, so
editing call sites is not the way. Expect a small vertical growth on cards — pair it with 6.3.

### 6.3 Directories are dense on desktop and endless on mobile

`/clubs` at 1440 px: three cards inside a 720 px column (≈200 px each). Titles wrap to two lines,
badges stack to three, descriptions truncate to "…recruitment, and…". At 390 px the same 35
organisations become a single column and the page is **10 315 px tall** with no pagination — the
filter panel alone (5 selects, 7 chips, Apply) occupies the entire first screen.

**Recommendation**
- Two columns at 720 px, three at ≥1024 px once 6.1 lands.
- Mobile: a "Filters (n)" button opening the existing panel as a sheet; keep the category chips
  as a single horizontal scroller.
- "Load more" or 12-per-page on both directories (`/clubs`, and `/market`, which is 4 757 px on
  mobile with 51 listings). The pagination pattern already exists in `/notifications`.

### 6.4 Other surface-level items

- The guide strip's decorative "tape" element (`span.guide-strip__tape`) reads as a broken
  image/skeleton placeholder at the strip's left edge — it is a light-grey bar with no content.
  Either give it texture or remove it.
- `/chat/[id]`: the "Reconnecting for live updates…" status line overlaps the composer's GIF
  button area at the bottom of the thread. It needs its own row above the composer.
- Notifications rows expose a bare `×` at the far right with no visible label; it is an icon-only
  control at 16 px. Add a tooltip/aria-label ("Dismiss") or drop it in favour of "Mark all read".
- `/profile` renders 20 chip buttons shorter than 24 px (WCAG 2.5.8 target-size, spacing
  exception aside). Same class of control as the ones on `/clubs`; give the chips min-height 32 px
  on touch.

## 7. State, correctness, and trust

### 7.1 Three unread numbers for two features

Measured on the fixture (verified directly against Postgres: **141 notifications, 36 unread** for
the signed-in student):

| Where | Shows |
|---|---|
| Sidebar Notifications badge | **36** (correct) |
| `/notifications` header | **"8 unread of 30"** — counts unread *among the 30 loaded rows* |
| Sidebar Messages badge | **36**, then **48** after opening one thread |

The first is right; the second is a page-scoped number presented as a global one; the third
changed direction on navigation in the harness (the client provider's snapshot and the server
render disagree). The messaging one may be a fixture artifact — the stub has no websocket — but it
is worth an assertion either way.

**Recommendation**
- `components/notifications/NotificationList.js` line ~101: take the *total* unread count from the
  server (the page already knows `count`) and word it `36 unread · showing the newest 30`.
- Add a test that pins badge == list total for a multi-page fixture.
- For messaging, assert `layout` badge === provider total after a conversation opens
  (`tests/navigation-messages.test.js` is the right home).

### 7.2 Search and "reconnecting" states are honest — keep that

Loading, empty and error states exist on every surface measured; `lib/data/*` returns
`{ items, unavailable }` rather than throwing. This is rarer than it should be and it shows.

### 7.3 The unauthorised-access story is genuinely strong

`/home`, `/profile`, `/settings`, `/admin` all redirect to `/login` when signed out; `/rules`,
`/legal`, `/guide` and `/timetable` are public by design; the API returns 401 for anonymous
`/api/search`. RLS + `can()` + column grants is the right layering, and `docs/SECURITY.md` is
accurate about it.

### 7.4 Bug fixed on this branch: `GET /api/giphy/search` answered 500 to everyone

**Symptom (reproduced live):**

```
GET /api/search?q=x              → 401 {"code":"unauthenticated"}
GET /api/giphy/search?q=test     → 500 {"code":"internal","error":"Something went wrong…"}
```

**Cause:** the catch block ended with

```js
return toHttpResponse(fromPostgresError(error) || error);
```

`fromPostgresError()` never returns a falsy value — its own fallback is `errors.internal()` — so
the `|| error` branch was dead code. Every `AppError` (401 anonymous, 403 `use_gifs`, 429 rate
limited) was converted into a 500 with a generic message.

**Fix:** `app/api/giphy/search/route.js` now maps only *non*-`AppError` values through
`fromPostgresError`, and adds a regression test (`tests/giphy-route-status.test.js`, 4 cases) that
pins 401 / 403 / 429 / 503. Verified live after restart: `401 {"code":"unauthenticated"}`.

This is the same class of bug described as open in `docs/CAMPUS_CONTEXT.md` §8.2-8 (only the form
had changed, so the document was right and the code had regressed).

## 8. Repository operations

### 8.1 There is no CI

`.github/` does not exist. The repository has 78 test files, 18 SQL suites, a lint config, a
service-worker freshness check, a SQL-bundle drift check, an architecture guard
(`tests/spec.test.js`) and a policy audit — and none of it runs on a push.

**Recommendation** — `/.github/workflows/ci.yml`, three jobs, no secrets needed:

```yaml
on: [push, pull_request]
jobs:
  web:    # ubuntu-latest, node 22
    steps: checkout → actions/setup-node cache:npm → npm ci
           → npm run lint → npm test → npm audit --omit=dev
  build:
    needs: web → npm run build (placeholder NEXT_PUBLIC_* values)
  db:
    services: postgres:17
    steps: supabase CLI start (or psql apply of supabase/bundle/campus-plus-schema.sql)
           → npm run verify:db
```

The `db` job is possible today because the SQL bundle is committed deliberately — that decision
now pays for itself.

### 8.2 The performance harness cannot run on a clean clone

`scripts/dev/perf/lib.mjs` imports `embedded-postgres`; `scripts/dev/browser.mjs` imports
`@sparticuz/chromium` and `playwright-core`. None is in `package.json`, and neither is in
`package-lock.json`. On a clean `npm ci`, `npm run perf:serve`, `perf:measure`, `perf:smoke`,
`test:contrast`, `visual-check` and `mobile-fit-check` all fail with `ERR_MODULE_NOT_FOUND`.
(I installed them by hand to run this audit.)

**Recommendation:** add them to `devDependencies` **or** — better, given their size — document
`npm i -D embedded-postgres @sparticuz/chromium` in `docs/PERFORMANCE.md` §2 and make the scripts
fail with a clear message (`throw new Error('Run: npm i -D embedded-postgres')`) instead of a
module resolver stack trace. Also note that `@sparticuz/chromium` is x64/Linux-specific; the
scripts should say so.

### 8.3 The documentation has drifted from the code

| Document | Says | Reality |
|---|---|---|
| `README.md` | "Campus+ UI and Home-feed performance patch" and instructions to `bash apply.sh` | This is a patch note for a bundle, kept as the repository front page. Nothing on it tells a new contributor what Campus+ is or how to run it. |
| `docs/ARCHITECTURE.md` §2 | "Email one-time-code only" | Google OAuth only (`lib/auth/oauth.js`, `app/auth/callback/route.js`) |
| `docs/CAMPUS_CONTEXT.md` | 24 migrations, 356 files, `CampusIntroLoader.js` (954 lines), 14 vitest files | 37 migrations, 318 JS files in `app/components/lib`, file is `components/layout/GalacticIntro.js` (396 lines), 78 vitest files |
| `docs/PERFORMANCE.md` | "migration 001 → 020", 34/36 migrations | 37 migrations |
| `docs/IMPLEMENTATION-REPORT.md` | 58 page routes, 53 permissions | 58 routes still true; permissions are 55 in `lib/constants.js` |
| `docs/SECURITY.md` §3 | 53 permissions | 55 |

The *documents themselves* are excellent — `2026-10-29-repository-wide-optimization.md` is a model
of honest measurement, including what was not measured. The problem is that nothing keeps them
true. `tests/bundle.test.js` already fails on SQL-bundle drift; the same trick works for docs:
assert that the migration count in `ARCHITECTURE.md` equals the number of files in
`supabase/migrations/`, and that the README's first paragraph names the app rather than a patch.

**README replacement sketch:** one paragraph on what Campus+ is and who it is for, a screenshot,
"Sign in with your PCCOE Google account", the stack, `cp .env.example .env.local` → `npm ci` →
`npm run dev`, a link map into `docs/`, and a "not affiliated with PCCOE" line. Move the current
content to `docs/patches/` if it is still wanted.

### 8.4 Repository weight

| Path | Size | Note |
|---|---|---|
| `docs/` | 7.7 MB | 38 PNG contrast-evidence files committed as proof |
| `perf-results/` | 5.2 MB | 93 JSON snapshots, including failed iterations |
| `.git` | 9.5 MB | |

Committing evidence is a defensible choice and the reports are honest about it. But 93 JSON files
in the default branch makes `git log`/review noisy, and the PNG evidence can be regenerated by
`npm run test:contrast`.

**Recommendation:** keep the *reports* (they are the value), move evidence to a release asset or
CI artifact, and add `perf-results/` retention (keep the three most recent named artifacts, as
the reports already do). A `docs/audit/` folder per audit, linked from a single index, beats
93 top-level files.

### 8.5 Two smaller DX items

- `package.json` has no `"type": "module"`, so direct Node execution of `lib/constants.js` warns.
  Harmless for Next/Vitest, but the `scripts/dev/*` tools are all ESM and would benefit.
- `lib/supabase/admin.js` (service-role client) has **no importers**. Unused privileged code is
  the kind of thing that gets used carelessly later. Either delete it or document in the file why
  it must not be imported by the app layer (the file header is good; a `tests/spec.test.js`
  assertion that no `app/` or `components/` module imports it would be better).

## 10. Performance: what is left, given what is already done

The repository has two serious performance reports and they are credible. Do not redo that work.
What remains, in order of user impact:

1. **The splash is the largest single LCP cost on `/home`.** 5,650 ms of overlay + up to 3,000 ms
   font wait + 283,656 bytes of preloaded fonts (`Syne.ttf`, `SpaceGrotesk.ttf`) on *every* Home
   document load. The route gate already exists (`shouldShowLandingIntro`); extending it to a
   session flag is a small change with a large perceived gain.
2. **`three.js` (0.164) for a decorative background.** `components/atmosphere/depth/createDepthField.js`
   and `ghost/createGhostScene.js` are lazily imported, which is the right call, but the library
   is still ~150 kB gzip when it loads and runs a continuous WebGL loop on the homepage.
   `DepthFieldFallback` is already a finished CSS composition. Consider: use the fallback on
   `prefers-reduced-data`, `saveData`, low `hardwareConcurrency`, and battery-saver; or drop the
   canvas entirely on mobile and keep it on desktop. Measure with the existing
   `perf-results` harness rather than guessing.
3. **Card-heavy directories.** `/clubs` is 1038 DOM nodes and 10 315 px tall on mobile, `/market`
   620 nodes / 4 757 px. Pagination helps the browser as much as the reader.
4. **Notification badge polling.** The 20-second refresh on focus (`UnreadNotificationsProvider`)
   is reasonable; make sure it stops when the tab is hidden (visibilitychange) — worth an
   assertion, since it is the only poll in the app.
5. **Keep the wins that exist.** The asset/prefetch work in `docs/performance/2026-10-29-*.md`
   (no logo preload on every route, no intro fonts outside `/home`, per-route brand derivative) is
   real and should not regress; add the assertions to CI so it cannot silently.

## 11. What not to change

Worth stating explicitly, because these are the parts a redesign would most likely damage:

- **The authorisation model.** UI hint + RLS + column grants, with `can()` failing closed. It is
  consistent across 58 routes and it is the reason this app can be trusted with student data.
- **The honesty of the copy.** "Ordered by the database, newest first — no ranking, no AI, no
  engagement theatre", "Private messages are never searchable", the legal/independence panel, the
  storage-unavailable fallback on the guide strip. This voice is the product's differentiator.
- **Error handling discipline.** `fromPostgresError` mapping, no raw SQL text in the UI,
  `{ ok, error, details }` everywhere. (The one bug in §7.4 was a misuse of it, not a flaw in it.)
- **Loading/empty/error states on every surface.** 24 `loading.js` files and honest empty states.
- **The test suite's architecture guards** (`spec.test.js`, `bundle.test.js`, `signout.test.js`).
  They catch the exact class of regression that bit the GIPHY route.
